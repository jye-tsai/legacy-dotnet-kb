ATLAS 系統介紹:六條業務線的端到端

給第一天接手 ATLAS、身邊沒有人可問的人。軸線是業務,不是技術也不是模組—— 開戶 → 申贖 → 結帳 → 庫存 → 報表,一條線讀到底。技術通則在 architecture.md、一模組一篇在 modules/README.md、操作步驟在 runbooks/README.md, 本篇只做抽取、整合與消歧,不重爬程式。內容是 2026-09-21 為止 29 篇模組文件與架構篇的彙整快照。 與現行程式不符一律以程式為準;標「假設」「推測」處代表 repo 內找不到權威來源。

0. 一頁摘要

素材:architecture.md §0、各模組篇 §0。

ATLAS(Vendor.Product.TA)是本投信的基金事務 / 過戶代理(Transfer Agency)系統,管投資人與基金之間每一筆事務的一生:開戶、申購、買回、轉換、定期定額、收益分配、對帳單與各式法定報表(architecture.md §0.1)。規模一句話:911 支畫面、437 張實體表、608 支報表範本、252 個專案。技術一句話:.NET WinForms 六層 + .NET Remoting(邊界在 UI 與 FormProxy 之間)+ Oracle + Crystal Reports, 四眼(EVA)是業務表的標準配備而非特例(architecture.md §0.4、architecture.md §0.5)。

四眼是什麼(白話):一筆資料要經過兩個人以上看過才算數——經辦鍵入(Entry)→ 覆核看過(Verify)→ 主管核准(Approve)。沒核准前它躺在「待辦」裡,不算正式資料;核准或退回都會留下誰、什麼時候。程式上靠表裡那 13 個欄位(CREATEID ENTRYID VERIFYID APPROVEID REJECTID STATUS…)記這件事。 兩個要先知道的例外:(1) 受益人資料變更是「覆核完還沒生效」,要等 OFDB003 那支批次跑過(bms.md §2.1); (2) 全庫有 36 支畫面 / 批次繞過四眼直接改正式表(§5 有清單)。

#業務線一句話
①開戶與受益人資料變更開一個受益人戶號,之後所有欄位異動都走「變更申請單」再由批次生效
②申購與定期定額櫃台 / 網路 / 語音三個入口收單,截止後拋轉進核心交易檔
③買回、轉換與受益憑證贖回與轉換的兩腳、匯費,以及實體 / 無實體受益憑證的狀態機
④結帳、庫存與日終關帳 → 日結轉 → 淨值配息 → 生效 → 產檔寄送,幾乎全部人工按鈕
⑤通路、業績與客戶關係代銷 / 直銷 / 電訪三種通路的名單、拜訪、目標、分帳與客訴
⑥報表、查詢與對外申報對帳單、法遵月報、通路分帳、境外平台交換,只讀不寫

另有不是業務線的底座:參數與代碼主檔(ofd123.md §0、ofd4.md §0、ofd5.md §0、ofd7.md §0、cod.md §0),六條線全部掛在它上面。三條軌先記住:ATLAS.OFD*(舊名 ATLAS.OFD*)是境內分戶軌、OTA* / OTAB 是境外綜合帳戶軌、EC* 是電子交易軌(ofdb5.md §0、misc.md §0、ofdi2.md §0);NFD 不是第四條軌,它是境內軌的純輸出層,沒有自己的表也沒有主專案(nfdr1.md §0、nfdr2.md §0)。

接手第一週讀什麼(細節見第 7 章):本篇 → architecture.md §1–§3 → 自己負責模組的那一篇 → runbooks/。

3.1 開戶與受益人資料變更

一位受益人從臨櫃送件開始。BMSM001(新戶)建檔走四眼三階段,落在 BMS001A 與它的明細;綜合帳戶的集保戶號與檢核碼不是程式產的,是 Trigger 給的(DB/Trigger/BMS001A_TDCC_BF_NO.SQL:230)。同時要做身分審查:OFDM123A 收投資屬性問卷與實質受益人、OFDM122A 收自主聲明書、OFDM157 維護高風險國別(ofd6.md §0);OFDM123A 的 SOURCE_CD 分「線上 / 後台 / 郵局」,選「線上」的資料禁止刪除 (Dev/ATLAS.OFD/Source/UI/UI.OFD/OFDM123A.cs:39)。網路開戶走 EC 軌收件,但主檔 OFD601 / OFD607A的唯一 xTableMapping 宣告在 BMS 那邊,EC 自己是裸 UPDATE(ec.md §0)。

這條線最要記住的一件事在「變更」不在「開戶」。受益人任何欄位要改,不是直接改 BMS001A,而是由 BMSM004 / BMSM006 開一張變更申請單 BMS001ACHG,一列同時帶 BEF_* 與 AFT_*。四眼覆核通過之後資料還沒進本表——判準是 TRIM(CHG_UPD_DTTM) IS NULL;要等批次 OFDB003呼叫 SP s_TA_OFDB003_Excute 才回寫並蓋上時戳(bms.md §2.1、 Dev/ATLAS.OFDB/Source/PO/PO.OFDB/OFDB003_PO.cs:64-78)。OFDB003 沒跑,下游印鑑與扣款批次就一直看到舊值。失敗會停在哪:OFDB003 執行前只詢問「還有幾筆沒覆核」,不阻擋(ofdb.md §6)。確認生效看 NFDR001「基金受益人名冊」(nfdr1.md §0)。

3.2 申購與定期定額

三個入口。櫃台由 OFDM221A 開申購書;「覆核才生效」在這裡不成立——真正的跨表副作用(更新過帳控制檔、櫃台控制檔、回寫贖回中單位數)掛在 AfterAdd / BeforeAdd,輸入按下去帳上就動了,四眼只是軌跡 (ofd8.md §0)。網路與語音由 EC 軌收單,到截止時間由 OFDB600 整批截單;它的時刻不在 Windows 排程器,而是 OFD606A 的四個截止時間欄與 OFD600A 的受益人變更時限,服務每 60 秒拿 HHmm 去比 (ofdb3.md §3、Dev/ATLAS.EC/Source/WindowsService/WindowsService.OFDB600/OFDB600_Service.cs:27-30、Dev/ATLAS.EC/Source/PO/PO.EC/Oracle/OFDB600OracleDao.cs:268-292)。截單後 OFDB601 / IPJB621 拋轉, OFDB605 會要求先跑過 OFDB600(ofdb3.md §3)。

定期定額是另一套契約:RSPM004 立約、RSPB020 改業務欄(代號是 B、其實是 M 畫面),扣款走RSPB009 產檔 → RSPB010 核印 → RSPB011 回覆 → RSPB018 結轉;扣款機構的簽約內容在 OFDM074(核印) 與 OFDM076(代理)(rsp.md §0、ofd5.md §0)。境外是鏡像的第二套:OFDB051 下單確認 →OFDB052 試算 → OFDB057 集保回報 → OFDB061 結帳,動的是不帶 A 的 OFD220 / OFD221(ofdb5.md §6)。

3.3 買回、轉換與受益憑證

OFDM231A 開買回書,而且它是全庫唯一會寫 OFD221A 的 RDMING_UNIT(贖回中單位數)的地方,寫法是繞過四眼引擎的手寫 UPDATE(ofd8.md §8)。贖回款匯出的匯費有兩組級距:OFDM035 全行通用、 OFDM036 個別銀行(ofd4.md §0)。但 repo 內沒有任何程式讀 OFD036A 去算一筆贖回實際要扣多少——計價流程在版控外(ofd4.md §0)。轉換是「贖回一腳 + 申購一腳」:可轉對應與費率在 OFDM085A / OFDM085B / OFDM086(ofd5.md §0),而申購日結轉 OFDB305 的第 12 道檢核就是「轉申購對應的贖回還沒結轉就擋住」(ofdb5.md §6)。

受益憑證是獨立的一套狀態機:BBSM001 換發、BBSM003 掛失、BBSM004 掛撤、BBSM005 補發、BBSM009 質設、BBSM010 質解、BBSM013 轉讓,每條線都有實體與無實體兩份(1xx 不是舊版,是無實體;bbs.md §0)。九個狀態值全部寫在 OFD721 的 CER_STATUS,值域在Dev/Common/Source/MappingCode/TA.MappingCode/CTL014.cs:2334-2372(bbs.md §2)。 同一張 OFD721 有兩組入口:BBS 那套走四眼,OFD 那套(OFDM721 OFDM723 OFDM724 OFDM725)自己下 SQL 不走四眼(ofd9.md §0)。CER_STATUS 的 '9'(已贖回)全庫查不到誰寫, 〔假設〕由贖回批次寫入(bbs.md §2)。

3.4 結帳、庫存與日終

一天的後半段:截止 → 關帳 → 日結轉 → 淨值配息 → 生效 → 產檔。OFDB222 逐基金逐銷售機構關帳,寫 CTL022 與 OFD303A(ofdb.md §0)。OFDB305(申購日結轉)有 12 道阻擋、OFDB323(買回)有 11 道, 全部寫在同一段 CASE WHEN 裡(ofdb5.md §6)。其中第 7 道「受益人暫停申購」自 2009 年起整段被註解(Dev/ATLAS.OFDB/Source/PO/PO.OFDB/OFDB305_PO.cs:245-260)——暫停申購的受益人擋不住日結轉。

淨值與匯率由 OFDM300 OFDM301 OFDM302 維護;境外軌另有 OFDM302B,匯入即鎖定而且完全繞過四眼(misc.md §0、Dev/ATLAS.OTA/Source/PO/PO.OTA/OFDM302B_PO.cs:208-209)。配息由 OFDB281 產生受益人清冊, 退匯 / 重匯是 OFDB286 / OFDB287(ofdb.md §0)。生效那一步就是 §3.1 講的 OFDB003。最後是產檔與媒體交換:OFDB565 傳檔 / OFDB566 收檔、集保上傳回收 OFDB716 ↔ OFDB721、核印扣款 OFDB701 → OFDB702 → OFDB703 → OFDB704(ofdb4.md §6)。失敗會停在哪:核印扣款那條七支流水線沒有任何一支在程式裡強制順序,靠資料狀態接力, 查不到資料就是空清單(ofdb4.md §6)。

3.5 報表與對外

報表線只讀不寫。對受益人的是 NFDR073「投資對帳單」與 NFDR076「申購交易確認書」(Dev/ATLAS.NFD.Report/Source/UI/ReportUI.NFD/NFDR073.cs:49);對主管機關的是 NFDR004 「員工及其關係人買賣本公司基金月報表」、NFDR006「債券型基金其他資訊揭露月報表」與公會英文申報NFDR558–NFDR560(nfdr1.md §0、nfdr2.md §0)。通路分帳由 CASM004 / CASM005 設比率, 而 CASB001 會直接 UPDATE 繞過四眼(cas.md §0)。境外平台交換是 OFDB600A / OFDB601A 那一群加 OTAB901(ofdb3.md §0、ofdb5.md §6)。報表是七層不是六層,多一層 Crystal Reports 專案 Report.<MOD>(ofdr1.md §0)。

4. 一日作業時序

5. 角色與四眼

素材:architecture.md §0.4、architecture.md §3、各模組篇 §0 與附錄 E。

§0 那個白話框講的「經辦 → 覆核 → 主管」三階段,程式上長這樣:

階段角色業務上的意思留下的欄位
Entry經辦我送出這筆異動CREATEID ENTRYID 及其 *DATE
Verify覆核我看過經辦送的內容VERIFYID VERIFYDATE
Approve主管我核准它生效,或退回APPROVEID / REJECTID 及其 *DATE

145 / 180 張有 xsd 欄位定義的實體表帶四眼欄位(81%),另外 257 張沒有 xsd 就無從判斷(architecture.md §0.4)。但「有四眼欄位」不等於「走四眼流程」,三種例外都要認得:(1) 四眼只是軌跡——OFDM221A / OFDM231A 的 AfterVerify / AfterApprove 沒有業務 SQL(ofd8.md §0);(2) 覆核完還沒生效——BMS 的 12 張 CHG 表要等 OFDB003(bms.md §2.1);(3) 一個人填滿三個欄位——整批匯入把 ENTRYID / VERIFYID / APPROVEID 塞同一人、STATUS 寫死 '301'(ofd7.md §0、misc.md §2)。
