# ATLAS 系統介紹:六條業務線的端到端

> 給第一天接手 ATLAS、身邊沒有人可問的人。**軸線是業務,不是技術也不是模組**—— 開戶 → 申贖 → 結帳 → 庫存 → 報表,一條線讀到底。技術通則在 `architecture.md`、一模組一篇在 `modules/README.md`、操作步驟在 `runbooks/README.md`, 本篇**只做抽取、整合與消歧**,不重爬程式。內容是 2026-09-21 為止 29 篇模組文件與架構篇的彙整快照。 **與現行程式不符一律以程式為準**;標「假設」「推測」處代表 repo 內找不到權威來源。

## 0. 一頁摘要

素材:`architecture.md §0`、各模組篇 §0。

ATLAS(`Vendor.Product.TA`)是本投信的**基金事務 / 過戶代理(Transfer Agency)系統**,管投資人與基金之間每一筆事務的一生:開戶、申購、買回、轉換、定期定額、收益分配、對帳單與各式法定報表(`architecture.md §0.1`)。規模一句話:**911 支畫面、437 張實體表、608 支報表範本、252 個專案**。技術一句話:**.NET WinForms 六層 + .NET Remoting(邊界在 UI 與 FormProxy 之間)+ Oracle + Crystal Reports**, 四眼(EVA)是業務表的標準配備而非特例(`architecture.md §0.4`、`architecture.md §0.5`)。

> **四眼是什麼(白話)**:一筆資料要**經過兩個人以上看過才算數**——經辦鍵入(Entry)→ 覆核看過(Verify)→ 主管核准(Approve)。沒核准前它躺在「待辦」裡,不算正式資料;核准或退回都會留下**誰、什麼時候**。程式上靠表裡那 13 個欄位(`CREATEID` `ENTRYID` `VERIFYID` `APPROVEID` `REJECTID` `STATUS`…)記這件事。 **兩個要先知道的例外**:(1) 受益人資料變更是「覆核完還沒生效」,要等 `OFDB003` 那支批次跑過(`bms.md §2.1`); (2) 全庫有 36 支畫面 / 批次繞過四眼直接改正式表(§5 有清單)。

| # | 業務線 | 一句話 |
|---|---|---|
| ① | 開戶與受益人資料變更 | 開一個受益人戶號,之後所有欄位異動都走「變更申請單」再由批次生效 |
| ② | 申購與定期定額 | 櫃台 / 網路 / 語音三個入口收單,截止後拋轉進核心交易檔 |
| ③ | 買回、轉換與受益憑證 | 贖回與轉換的兩腳、匯費,以及實體 / 無實體受益憑證的狀態機 |
| ④ | 結帳、庫存與日終 | 關帳 → 日結轉 → 淨值配息 → 生效 → 產檔寄送,幾乎全部人工按鈕 |
| ⑤ | 通路、業績與客戶關係 | 代銷 / 直銷 / 電訪三種通路的名單、拜訪、目標、分帳與客訴 |
| ⑥ | 報表、查詢與對外申報 | 對帳單、法遵月報、通路分帳、境外平台交換,只讀不寫 |

另有**不是業務線的底座**:參數與代碼主檔(`ofd123.md §0`、`ofd4.md §0`、`ofd5.md §0`、`ofd7.md §0`、`cod.md §0`),六條線全部掛在它上面。**三條軌先記住**:`ATLAS.OFD*`(舊名 `ATLAS.OFD*`)是境內分戶軌、`OTA*` / `OTAB` 是境外綜合帳戶軌、`EC*` 是電子交易軌(`ofdb5.md §0`、`misc.md §0`、`ofdi2.md §0`);`NFD` **不是第四條軌**,它是境內軌的**純輸出層**,沒有自己的表也沒有主專案(`nfdr1.md §0`、`nfdr2.md §0`)。

**接手第一週讀什麼**(細節見第 7 章):本篇 → `architecture.md §1`–`§3` → 自己負責模組的那一篇 → `runbooks/`。

## 5. 角色與四眼

素材:`architecture.md §0.4`、`architecture.md §3`、各模組篇 §0 與附錄 E。

§0 那個白話框講的「經辦 → 覆核 → 主管」三階段,程式上長這樣:

| 階段 | 角色 | 業務上的意思 | 留下的欄位 |
|---|---|---|---|
| Entry | 經辦 | 我送出這筆異動 | `CREATEID` `ENTRYID` 及其 `*DATE` |
| Verify | 覆核 | 我看過經辦送的內容 | `VERIFYID` `VERIFYDATE` |
| Approve | 主管 | 我核准它生效,或退回 | `APPROVEID` / `REJECTID` 及其 `*DATE` |

**145 / 180 張有 xsd 欄位定義的實體表帶四眼欄位(81%)**,另外 257 張沒有 xsd 就無從判斷(`architecture.md §0.4`)。但**「有四眼欄位」不等於「走四眼流程」**,三種例外都要認得:(1) **四眼只是軌跡**——`OFDM221A` / `OFDM231A` 的 `AfterVerify` / `AfterApprove` 沒有業務 SQL(`ofd8.md §0`);(2) **覆核完還沒生效**——BMS 的 12 張 `CHG` 表要等 `OFDB003`(`bms.md §2.1`);(3) **一個人填滿三個欄位**——整批匯入把 `ENTRYID` / `VERIFYID` / `APPROVEID` 塞同一人、`STATUS` 寫死 `'301'`(`ofd7.md §0`、`misc.md §2`)。
